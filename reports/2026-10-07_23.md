## Décisions techniques et raisons
- **Utilisation d'environnement factice (dummy) pour le build CI :** Next.js requiert certaines variables lors de la phase de build (comme `DATABASE_URL` pour les scripts de vérification Drizzle ou `BETTER_AUTH_SECRET`). Plutôt que d'exposer des secrets de production dans GitHub Actions ou de créer une base de données de build, j'ai injecté des valeurs "dummy" dans `env` pour permettre au build statique de passer.
- **`bun test` via `bun run test` :** Bien que l'outil utilise nativement bun, j'ai configuré la commande `bun run test` dans la CI pour m'assurer que le script défini dans `package.json` (qui utilise Vitest comme runner) soit bien utilisé, évitant les erreurs de polyfill inhérentes au testeur natif de bun, comme documenté dans la mémoire de projet.
